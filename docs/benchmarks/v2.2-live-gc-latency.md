# V2.2 live-victim GC latency experiment — design gate

**Status (2026-10-08): SOURCE-ONLY DESIGN + OFFLINE ANALYZER. No GC-trigger or GC-overlapping swap-in latency measurement has been run.** Do not use this document to select the V2.2 strategy or physical batch size.

## Evidence already available

The 2026-10-08 Codex report for kernel candidate `d35455ec146ffed7aaed08a001764cd0e05324dd` reports 100,000-operation randomized suites, exact 30,000-operation/117-checkpoint live-GC readback, and 116 relocated pages for both opportunistic and staged. The no-lower-DISCARD opportunistic case also had 116 relocations; all three had `failed=0`. Two bounded swap-pressure holds passed per strategy at a matched 16 KiB batch, including swapoff and second activation. These are correctness/progress results, **not** measured GC-trigger or live-GC swap-in tail latency.

The report identified teardown problems in the no-DISCARD and staged-recall fixtures. Those source paths now use `tests/runtime/test-stack-teardown.sh`; independent runtime revalidation remains pending.

## Kernel path and definitions

Source: `kernel/dm-swapz.c`, current V2.2.

- `swapz_ensure_physical_block()` flushes the stream and calls `swapz_advance_segment()` when the current physical segment is exhausted.
- `swapz_advance_segment()` opens a destination and calls `swapz_clean_segment(context, victim)` when it must restore the last free-segment reserve.
- `swapz_clean_segment()` changes the victim state to CLEANING, increments `gc_victims`, scans mappings, reads live 4 KiB containers, relocates pages, flushes writes, optionally discards, and returns the victim to FREE. The cumulative `compaction_pages` counter is exposed in DM status as `gc_pages`.

Measure **distinct, explicitly named intervals**:

1. **GC-body duration:** entry to return from `swapz_clean_segment()`, including its live-record copying and lower I/O; zero-live victims are separately classified.
2. **Rotation/trigger duration:** entry to return from `swapz_advance_segment()`, including reserve management and GC, but not the preceding flush in `swapz_ensure_physical_block()`.
3. **Foreground BIO completion latency:** arrival to final completion for the affected write, including queued-worker time and buffer draining; it is not interchangeable with GC-body latency.
4. **Swap-in completion latency:** userspace direct-read submission to successful completion, separately for reads overlapping a verified live-GC interval and reads outside it.

A long read overlapping GC is **correlated** with GC, not automatically caused by GC. Reads from staged RAM must remain distinguishable from physical reads.

## Data collection — prerequisites

No physical devices are authorized. Begin only after the source-only teardown gates pass and a separate bounded virtual-runtime handoff is approved.

1. Record tested Git SHA, `uname -r`, kernel source identity, built and loaded module `srcversion`, batch ceiling, strategy, compressibility, QD, workload seed, tracing settings and exact command.
2. First inspect availability of read-only `tracefs` function-graph/fprobe/kprobe mechanisms for the named functions. Do not depend on symbols being exposed or on a specific kernel offset.
3. Use one clock domain: `CLOCK_MONOTONIC` nanoseconds for userspace read completion and verified matching `trace_clock=mono` for kernel windows. Validate alignment with calibrated trace markers or equivalent monotonic timestamps; never combine uncalibrated trace-clock, realtime, or MONOTONIC_RAW values.
4. Per **individual** GC call, capture entry, exit, error, and actual moved-page count. The cumulative `gc_pages` delta proves a run had relocations, but **cannot** tag which GC interval contained live relocation. Function-graph durations alone therefore cannot produce a valid per-event `moved_pages` field.
5. If per-event relocation cannot be measured reliably using existing tracing, stop at an instrumentation design. A separate reviewed, test-gated tracepoint/counter change is required before claiming exact live-GC overlap latency. Do not read private struct offsets with unreviewed BPF probes or modify the validated kernel opportunistically.
6. Independently timestamp every foreground swap-in READ with its error status and verify expected bytes. Use bounded preallocated, 4 KiB-aligned direct-I/O buffers and a predictable QD1 reader; keep workload writes concurrent on a separate bounded worker. Avoid timestamps written through a buffered file in the hot path.
7. Prove sustained **live** relocation with `gc_pages` increasing, `gc_read > 0`, `gc_write > 0`, exact reference-driven readback, `failed=0`, and full drain at the end. Report empty victims separately.

## Offline data format

`tests/runtime/live-gc-latency-analyze.py` accepts two UTF-8 CSV files with absolute, common `CLOCK_MONOTONIC` nanoseconds.

`gc.csv`:

```csv
clock,start_ns,end_ns,moved_pages
monotonic,1000000000,1010000000,2
```

`reads.csv`:

```csv
clock,start_ns,end_ns,result
monotonic,1005000000,1007000000,ok
```

The analyzer:

- Rejects invalid or mixed clocks, reversed intervals, unsuccessful reads, zero live-GC events, and too few overlapping reads.
- Merges overlapping live-GC windows and classifies any read interval that intersects a window with `moved_pages > 0`.
- Reports nearest-rank p95, p99, maximum and sample counts for all reads, overlapping-live-GC reads, and outside-GC reads.
- Defaults to a **10,000 overlapping-read** minimum for qualification; use a lower `--min-overlap-reads` only for explicitly labeled pilot analysis.
- Does not itself verify the trustworthiness of collected timestamps or per-event relocation data.

Source-only regression:

```bash
python3 tests/runtime/live-gc-latency-analyze-test.py -v
```

Once genuine, independently validated CSV inputs exist:

```bash
python3 tests/runtime/live-gc-latency-analyze.py \
  --gc-events gc.csv --reads reads.csv --min-overlap-reads 10000
```

## Experimental plan and acceptance

Begin with one bounded synthetic/virtual case per strategy using matched QD, seeds, 50% compressibility and an experimental 16 KiB batch (not a shipping default). Keep a fixed known read set and deterministic churn. Check source-only safety first; preflight host ownership, expected swap and loaded-module identity before any runtime work. Increase case duration only after progress, exact readback, and teardown are proven.

For the initial latency-gate report, record GC-body duration p50/p95/p99/max (and count), rotation duration, foreground write/reclaim completion latency, read p95/p99/max with counts in **both** GC-overlap and outside-GC classes, total physical bytes including GC, CPU overhead, staged reads/cancellations and per-run trace overhead. Repeat with tracing disabled to quantify instrumentation cost.

A qualifying comparison requires:

- Exact readback and clean callback/stream drain; `failed=0`; no unexplained DM/block/kernel errors.
- Actual **per-event** live relocation, not only nonzero `gc_victims`; trace event count and moved-page totals reconciled against DM status.
- Matched tested kernel/module, strategy configurations, seeds and clock domain; no lost trace events.
- At least 10,000 correctly classified overlapping reads for a primary p99 estimate; report counts and any smaller pilot runs without claiming qualification.
- Verified teardown of exact test targets before loop/NBD disconnection; normal host swap untouched.
- No interpretation of staged early upper completions as end-to-end physical drain.

Do not choose a winner solely from these timings. The 20 MiB/s large-request plateau still requires separate **calibrated** size-aware NBD and subsequently authorized physical-media evidence.
