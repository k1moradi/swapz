# V2.2 rootless benchmark plan and pre-device size admission

## Why this gate is necessary

The V2.2 comparison has three policies: `immediate` (4 KiB
control), `opportunistic`, and `staged`. The existing
`streaming-benchmark.sh` operates on a disposable kernel
`null_blk` fixture, requires root and creates a Device Mapper
target; **none of those operations is required to inspect the plan**.

The default backend's bandwidth throttle replenishes once every
1/50 second. Its maximum serviceable request size is limited by the
current tick's byte credit, **not** the average MiB/s bandwidth.

At 20 MiB/s the configured budget is

```text
(1048576 // 50) * 20 = 419420 bytes (~409.6 KiB)
```

A throttled 512 KiB or 1 MiB write therefore cannot complete under
that particular synthetic backend. The old live benchmark default
included both sizes and checked that error only *after* creating a
`null_blk` fixture. This is a benchmark admission defect, not a
normal swapz I/O defect.

## New rootless planning command

```bash
python3 -B tests/runtime/streaming-benchmark-plan.py \
  --backend null_blk --mbps 20 \
  --strategies "immediate opportunistic staged" \
  --batches auto --repeats 3
```

The planner reads only its CLI arguments, validates ranges and
emits JSON. It does not open /dev, sysfs, mount information, host
swap, sockets, or a kernel module; it does not execute a benchmark.

Its default 20 MiB/s plan contains **15 unique configurations**:

- Immediate: 4 KiB baseline (one case)
- Opportunistic: 4, 8, 16, 32, 64, 128, 256 KiB (seven cases)
- Staged: the same seven cases

Three planned repetitions yield **45 proposed observations**,
not 45 measurements. Actual independent repetitions and trustworthy
counter/latency provenance are still required for any plateau decision.
The current privileged streaming benchmark continues to execute a
single diagnostic sweep per invocation.

Inspect a proposed 512 KiB / 1 MiB NBD experiment, **without enabling
NBD execution**, with:

```bash
python3 -B tests/runtime/streaming-benchmark-plan.py \
  --backend nbd --mbps 20 \
  --batches "512 1024"
```

The JSON explicitly marks `backend_runnable=false` and
`evidence=PLAN_ONLY_NO_MEASUREMENTS`. The NBD runner in the
benchmark remains **hard-disabled** pending reviewed pidfd-owned
process lifecycle, explicit selection of a disposable unused virtual
NBD node, native smoke tests, exact readback and calibrated measured
request sizes. Do **not** remove that guard or force-detach a target.

At `--mbps 0` all supported batch sizes fit because there is no
bandwidth throttle; that is a **latency/overhead control only** and
cannot establish a 20 MiB/s throughput plateau.

## Live script integration and safety

The existing `streaming-benchmark.sh` now calls the rootless
planner's `--emit-batches` mode **before** EUID/root checks, module
load, configfs setup or temporary file allocation. It validates:

- Allowed strategy names with no duplicates
- Strictly increasing supported batch ceilings
- Null_blk per-tick budget for nonzero bandwidth, including explicit
  rejection of 512/1024 KiB at 20 MiB/s
- Finite allowed bandwidth/latency and bounded fio runtime,
  writer queue depth and compression percentage
- Immediate 4 KiB control remains exactly one case

With no explicit `SWAPZ_BENCH_BATCHES`, the live 20 MiB/s runner
uses the automatically admitted 4–256 KiB set. An explicitly unsafe
list fails **before any fixture is allocated**. The former later
post-setup bound guard is retained as defense in depth.

The benchmark remains root-required and operation on its disposable
kernel virtual devices is **not authorized by planning or source-only
CI**. Before future authorized virtual runs, explicitly verify host
device identity, no unrelated holders, no active host swap involvement,
safe failure cleanup, pinned executable module revision, and absence
of residual test-owned state. Physical storage remains out of scope.

## Measurement validity

The live runner also verifies that the resolved `fio --version` has the
Flexible I/O Tester `fio-N.N` identity **before any device allocation**;
a same-named Python Fiona CLI must not pass admission. A negative rootless
test supplies a mock Fiona binary on `PATH` to prove this fail-closed rule.

The existing `streaming-benchmark-report.py` is intentionally a
**single-sweep, non-qualifying diagnostic reporter**. It cannot
prove complete physical drain, independent backend attribution, a
repeated p99 estimate, or a winner. Its lower-counter-window rate
is not interchangeable with logical upper-write completion speed.

The existing strict
`tests/runtime/v22-drain-plateau-analyze.py` and V3 latency evidence
bundle tools are the future assessment path after an independently
trusted collector is available. A nominal policy/batch winner must
not be reported until evidence includes:

1. Pinning of the exact executable kernel source and module identity.
2. A qualified backend in a separately authorized disposable virtual
   test fixture, with safe setup and verified clean teardown.
3. Actual lower-device sector/IO counters and complete drain.
4. At least three independent matched runs per candidate.
5. Adequate concurrent read-latency observations, with independently
   attributable p99 and exact sidecar integrity where applicable.
6. Comparable compressibility, queue depths, latency, workload and GC.
7. A Pareto decision meeting the existing 97% lower-drain plateau
   and within 10% of best plateau read p99, preferring the smallest
   acceptable batch. If evidence stops at 256 KiB while improvement
   is still possible above it, report **PLATEAU NOT REACHED**.

The planner and source-only tests cannot establish any of these
measurements. V2.2 strategy and batch winner remains **UNDETERMINED**.

## Exact fio reader-CLAT diagnostics (source-only extension)

The live runner now requests unaveraged `fio` read-completion latency logs
(`write_lat_log`, `log_avg_msec=0`, and `per_job_logs=0` on its single reader).
After fio completes, the bounded rootless
`tests/runtime/streaming-benchmark-read-latency.py` helper verifies every
4 KiB read sample against `reader.read.total_ios` in the exact fio JSON.
It rejects missing, extra, non-read, malformed, zero-latency, nonmonotonic,
oversized or aggregated samples rather than substituting fio's summarized p99.

It emits sorted, run-length-encoded `!QQ` V3 latency records and reports a
SHA-256 digest, exact nearest-rank p99 and actual sample count. The existing
V3 sidecar reader is exercised in the rootless regression suite. These
artifacts are *diagnostic*: they do not independently prove workload/device
identity, lower-counter attribution, complete drain, quiescence or matched
repeatability. The live JSONL is still the single-sweep diagnostic format,
**not** `swapz-drain-observation-v3`, and no winner is nominated.

The temporary exact fio logs and sidecars are deleted after successful
teardown by default. An explicitly authorized live virtual test may set
`SWAPZ_BENCH_KEEP_ARTIFACTS=1` to preserve its temporary directory after
verified target/backing cleanup. Retention is validated before setup and
never permits extra device operations; on an error existing teardown
preservation rules apply. The bounded source-only helper can be exercised
without any kernel or device activity:

```bash
python3 -B tests/runtime/streaming-benchmark-read-latency-test.py -v
```

The collector deliberately bounds fio logs at 64 MiB and exact reader
samples at 500,000 per run. The default 100 reader IOPS and three-second
workload remain fast diagnostic settings, not statistically sufficient
qualification. `SWAPZ_BENCH_READ_IOPS` now accepts 1..2000 positive decimal
IOPS, validated **before** root checks or fixture allocation. The runner
preallocates 32768 fio latency log entries to avoid routine log-buffer growth
for common exploratory runs. A rate is only a *target*: count actual read
completions and require at least 10,000 in every eventual qualifying run.

The displayed `read_p99_ms` is now the nearest-rank p99 computed from the
validated exact reader CLAT samples; `fio_summary_read_p99_ms` is retained
separately for comparison. The sysfs counter/timer window stops **immediately
after the explicit target flush**, before Python CLAT parsing. It includes the
fio operation and flush latency but excludes log conversion overhead; it still
does not independently establish quiescence, backend attribution or a
qualified physical-drain rate.

## First exploratory virtual-device comparison (operator plan; NOT run)

**Prerequisite:** Codex's isolated-VM smoke gate must pass on an explicitly
authorized, test-owned disposable virtual fixture, including deterministic
Staged RAM readback before lower completion, post-drain readback and safe
teardown. Source-only CI is not authorization to run this benchmark. The
existing runner performs privileged null_blk and Device Mapper operations;
never invoke it on the host, shared checkout or any physical backing device.

Inside that separately authorized VM, after checking that `fio --version`
identifies the real Flexible I/O Tester (not an unrelated Python `fio` CLI),
the following environment expresses the **proposed** initial sweep:

```bash
SWAPZ_BENCH_BACKEND=null_blk \\
SWAPZ_BENCH_MBPS=20 \\
SWAPZ_BENCH_LATENCY_NS=500000 \\
SWAPZ_BENCH_RUNTIME=30 \\
SWAPZ_BENCH_READ_IOPS=500 \\
SWAPZ_BENCH_BATCHES='4 8 16 32 64 128 256' \\
SWAPZ_BENCH_STRATEGIES='immediate opportunistic staged' \\
SWAPZ_BENCH_KEEP_ARTIFACTS=1 \\
tests/runtime/streaming-benchmark.sh
```

This proposes 15 independent *configurations*, one diagnostic pass each.
500 IOPS for 30 seconds **targets**, but does not guarantee, 15000 reader
completions; delay, contention, host load or stalls can reduce that count.
Report actual counts and abort or lengthen the authorized measurement when
insufficient. All upper I/O remains 4 KiB. Compare exact concurrent read p99,
upper logical throughput, lower-device sector/write-IO deltas, flush-inclusive
window, and the target's failed/staged/maximum batch counters. Treat fio
writer throughput as logical ingress, not physical drain. Neither a 50%
compressibility knob nor a high lower sector rate certifies a specific
compression ratio, readback integrity, clean GC or independent attribution.
The runner also now reserves the final, non-overlapping 4 KiB logical
page outside the fio writer's extent. Before the timed window it writes a
known compressible byte pattern and explicitly flushes it. **After** the fio
and flush-inclusive lower-I/O counter snapshots, it reads that page directly
and checks exact byte parity. A failed readback aborts the case and prevents
publication of a plausible-looking benchmark row. The result field
`isolated_sentinel_readback_ok=true` asserts **only this one page**; it is
not a full integrity check of fio's randomly overwritten pages. The
sentinel's pre-write and post-read are excluded from the timed sector window.
An unprivileged, two-job real-fio integration test additionally checks that
fio's actual offset/size semantics leave this sentinel untouched.

The collector now rejects any nonzero/missing fio job-level error, missing or
duplicate writer/reader job, or decreasing physical read/write counter;
these errors fail closed rather than being hidden by aggregate throughput.

### Complete configured writer-range checksum readback (still diagnostic)

For every policy/batch, the runner now **prefills the complete 4 KiB-aligned
writer region** with fio CRC32C verification headers before the timed window.
Timed 4 KiB random writes use `verify=crc32c` and `do_verify=0`, so they
update those headers without running an unintended verification phase inside
the concurrent reader/writer measurement. This changes the synthetic payload
and imposes a small checksum cost on each timed write, shared by all policies;
it must be included when interpreting measured CPU and compression ratios.

After fio completes and the explicit flush finishes, the lower-device
sector snapshots and monotonic clock stop. **Only then** a distinct fio
`writer-verify` job sequentially reads the entire configured writer extent,
verifying each 4 KiB page's offset-aware CRC32C header. The bounded rootless
`streaming-benchmark-writer-verify.py` validator checks that exactly
`28 MiB - 4 KiB = 29,356,032 bytes = 7,167 pages` were read, fio reports
zero job errors and no write I/O, and the declared identity and input file
are sound. A mismatch aborts the case; no result row is published.
`fio_full_writer_verification.full_writer_readback_ok=true` means fio
completed that checksum pass. The separate protected sentinel still checks
a known exact page outside the writer extent.

This covers the **entire configured writer region** and distinguishes
sequential prefill pages from pages overwritten during the timed random
workload. It does *not* independently authenticate the source device,
verify fio's data generation against an external oracle, attest physical
quiescence, certify a checksum-collision-free identity, or establish a
qualifying benchmark winner. The verification reads are intentionally
excluded from measured read p99 and timed physical-counter throughput,
and can increase total per-case wall time substantially.

A real rootless fio regression on an ordinary file proves that a timed
random writer with CRC headers is subsequently readable and that one
deliberately flipped payload byte is rejected. This is not a loaded-kernel
test. No change to `kernel/dm-swapz.c` or Codex's isolated-VM smoke harness
is involved.

The strict V3 offline plateau evaluator remains a **separate gate** requiring
at least three independent samples per candidate, full batch coverage and
qualified lower I/O provenance. The full configured writer-range CRC check
helps detect data corruption but does not automatically satisfy the V3
`integrity_ok` provenance contract.

The exact fio CLAT filename and field semantics are specified in the fio
manual: `<prefix>_clat.log` with `per_job_logs=0`; per-I/O CLAT values are
nanoseconds and direction `0` denotes read. Synthetic rootless CI checks
the converter, but a genuine fio regular-file smoke is still needed before
asserting that the live runner's exact log capture is operational.


## Fast first-data path: three strategy cases (source-only preparation)

To minimize the delay between **authorized loaded-kernel smoke PASS** and
first performance data, begin with precisely three cases rather than fifteen:

| Strategy | Lower batch ceiling |
| --- | --- |
| immediate | 4 KiB (forced baseline) |
| opportunistic | 64 KiB |
| staged | 64 KiB |

The existing planner and privileged runner already support this subset:
`SWAPZ_BENCH_BATCHES='64'` runs the Immediate control once at 4 KiB,
then Opportunistic and Staged at 64 KiB. **Every upper BIO remains 4 KiB.**

Use the new source-only manifest to cross-check the intended configuration
*without any device access or subprocess execution*:

```bash
python3 -B tests/runtime/v22-fast-screen.py --plan fast
python3 -B tests/runtime/v22-fast-screen.py --plan full
```

The first command describes the following **proposed operator environment**.
It does NOT authorize benchmark execution, and these settings must be used only
on a separately authorized, disposable VM **after** Codex's reviewed smoke
harness passes and the executable swapz module/revision is pinned:

```bash
SWAPZ_BENCH_BACKEND=null_blk \
SWAPZ_BENCH_MBPS=20 \
SWAPZ_BENCH_LATENCY_NS=500000 \
SWAPZ_BENCH_RUNTIME=10 \
SWAPZ_BENCH_READ_IOPS=300 \
SWAPZ_BENCH_QD=64 \
SWAPZ_BENCH_COMPRESS=50 \
SWAPZ_BENCH_BATCHES=64 \
SWAPZ_BENCH_STRATEGIES='immediate opportunistic staged' \
SWAPZ_BENCH_KEEP_ARTIFACTS=1 \
SWAPZ_BENCH_DISCARD=0 \
tests/runtime/streaming-benchmark.sh
```

**This command is illustrative, not an instruction to execute now.** It performs
privileged virtual-device setup, requires separately authorized actions, and
is not run by the rootless manifest or regression suites.

The first screen has only **30 seconds of nominal timed fio duration** across
three cases. Total wall time is greater and can be much greater: independent
per-case cold prefill, full writer-range CRC prefill, flush, all-page CRC
readback, safe DM teardown and virtual-device setup are excluded from the
10-second timed window. The nominal 300 IOPS × 10 seconds ≈ 3000 read
completions per case is **not a guarantee**. A 10-second screen is not
statistically comparable to the future three-repetition, ≥10,000-read-per-run
V3 qualification.

### Fail-closed post-run rootless check

After an authorized VM run completes with clean verified teardown and
`DIAGNOSTIC_ARTIFACTS` points to its preserved artifact directory, inspect
the JSONL and all three exact CLAT sidecars **without touching devices**:

```bash
python3 -B tests/runtime/v22-fast-screen.py \
  --results "/path/to/preserved/diagnostics/results.jsonl"
```

The read-only gate requires exactly the three cases in expected order;
the exact 20 MiB/s / 500,000 ns / QD1 `null_blk` backend; matching kernel
`strategy`, `batch_kib`, `lower_discard=off`, `failed=0` statuses;
positive lower write requests/sectors; full writer CRC32C and protected
sentinel checks; **at least 1000 actually observed reads per case**; and
read p99/count/digest independently recomputed from the pinned V3-compatible
CLAT sidecars. Missing, corrupt, symlinked, reused, incomplete or inconsistent
artifacts fail the gate. The 1000-sample exploratory floor is a guardrail
for a quick screen, **not** formal p99 qualification.

A success returns `PASS_SOURCE_REPORTED_ONLY`, not a qualified winner:
source-reported fio and status cannot independently certify the device,
module provenance, quiescence or backend-I/O attribution. Follow that result
with kernel warning review, VM fixture teardown/provenance review, and a
decision whether the three strategies merit the **full 15-case** exploratory
matrix (30 seconds and 500 reader IOPS target per case), as emitted by
`--plan full`. Keep the strict V3 plateau evaluator separate.

Only advance from the smoke to the screen, or from screen to full sweep,
when those additional authorized runtime checks pass. Do not enable NBD or
unsafe 512/1024 KiB batches at the default 20 MiB/s `null_blk` setting.
